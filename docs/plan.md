# Claude Code Dashboard 実装方針 (docs/plan.md)

## 前提パラメータ（会話コンテキストより確定）

- **テーマ**: Claude Code Dashboard — Claude Codeとの協働における「ルール」「実行ログ／思考プロセス」を可視化・管理するローカルWebダッシュボード
- **目的**: Claude Codeへの指示ターン数を削減し「1-Shot完了」を実現するため、ルール管理（機能1）・実行ログ/手戻り可視化（機能2）をGUI化し、ユーザーの暗黙知をルールとして蓄積する
- **対象**: Claude Codeで業務資料作成・開発タスクを行う実務者本人。将来複数プロジェクトを横断利用
- **制約**（前ターンでユーザー合意済み）:
  - 対象スコープ：複数プロジェクト横断管理（`config/projects.json` でプロジェクトパスを登録・切替）
  - フレームワーク：Next.js 14 (App Router) + TypeScript + Tailwind CSS + shadcn/ui + Recharts（Streamlit不採用、デザイン自由度優先）
  - Webアプリ側はCPUモードでは外部API通信なし。ローカルJSON/MDファイルの読み書きのみ
  - GPUモード（Ollama連携によるルール矛盾検出＝機能3／Phase4）は**今回のスコープ外**。導線・型定義のみ用意し、実装は次回タスクとする
  - 初期データは仕様書記載のサンプルJSONをそのまま使用
  - 進め方：段階的Phaseではなく主要機能（機能1・機能2）を一括実装
- **auto_drive**: 明示指定なし。ただしハーネスのAuto Mode Activeが有効なため、都度の承認待ちはスキップし合理的判断で進行（判断根拠は本ファイルに記録）

## 仮定（未確定事項の自己補完）

1. `execution_log.json` は仕様書サンプルでは単一オブジェクトだが、時系列ログという性質上、実運用では複数タスク分蓄積されると判断。**配列で複数タスクを保持**する形に拡張する（サンプル1件を配列の初期値として格納）。一覧→詳細ドリルダウンのUIとする。
2. プロジェクトごとの `rules.json` / `execution_log.json` / `CLAUDE.md` の実体パスは、`config/projects.json` に登録した各プロジェクトルート直下に存在する前提とする（本仕様書のデータ構造定義に準拠）。
3. 複数プロジェクト管理のうち「本プロジェクト自身」もダミープロジェクトとして `sample-data/` を初期登録し、動作確認できるようにする。
4. ルールの「有効/無効」トグルは `rules.json` の `enabled` を書き換えるのみとし、`CLAUDE.md` 側は `enabled: true` のルールのみを本文に反映する形で同期する（無効ルールは `CLAUDE.md` に書き出さない）。

## 1周目：方向性

### 戦略家

- ニッチだが競合不在の個人生産性ツール。差別化価値は「複数プロジェクト横断でのルール一覧性」「トグルON/OFFの手軽さ」「手戻り原因の自動可視化」。
- 想定される反論「CLAUDE.mdを直接編集すればいいのでは」に対しては、カテゴリ整理・有効/無効切替・履歴を伴う可視化がGUI側の付加価値であり、CLAUDE.md直接編集を代替するものではなく補助する位置づけとする。
- 勝ち筋：CPUモードでの軽量・即時反映・オフライン動作を徹底し、日常的に開く「振り返りダッシュボード」として定着させること。

### 設計者

- ページ構成：`/`（プロジェクト選択）, `/rules`（機能1）, `/trace`（機能2）, `/refactor`（機能3・スコープ外だが導線のみ）
- データフロー：`config/projects.json` に現在選択中プロジェクトの絶対パスを保持 → 各APIルートが選択中プロジェクト配下の `rules.json` / `execution_log.json` / `CLAUDE.md` を直接読み書き
- 主な失敗リスク：
  - JSON構文エラー時の全体クラッシュ → パース失敗を検出し、エラーバナー表示にとどめる（アプリを落とさない）
  - Windowsパス処理（バックスラッシュ・日本語パス）
  - 同時書き込みによる競合（単一ユーザー利用前提のためロックは簡易実装に留める）
  - `CLAUDE.md` とルールDBの二重管理による不整合 → ルールブロックをマーカーコメントで区切り、そこだけを自動生成・上書きする方式にする

### 生成者：3案比較（データ取得・状態管理方式）

| 案 | 内容 | 評価 |
|---|---|---|
| A. ステートレスAPI + クライアントSWR | API Routeは読み書きのみ、フロントはSWRで取得しトグル操作は楽観的更新 | シンプル・単一ユーザー用途に十分。**採用** |
| B. サーバー側インメモリキャッシュ+同期 | サーバーでキャッシュ保持し変更を都度ファイル同期 | 単一ユーザーローカル利用では複雑さに見合う恩恵がない |
| C. WebSocketでリアルタイム同期 | ファイル変更を監視しプッシュ通知 | 過剰設計。CPU軽量方針に反する |

→ **案Aを採用**。API Routesはファイル直接読み書きのみのステートレス設計とし、フロントはSWRで再検証する。
