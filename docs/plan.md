# Claude Code Dashboard 実装方針 (docs/plan.md)

## 前提パラメータ（会話コンテキストより確定）

- **テーマ**: Claude Code Dashboard — Claude Codeとの協働における「ルール」「実行ログ／思考プロセス」を可視化・管理するローカルWebダッシュボード
- **目的**: Claude Codeへの指示ターン数を削減し「1-Shot完了」を実現するため、ルール管理（機能1）・実行ログ/手戻り可視化（機能2）をGUI化し、ユーザーの暗黙知をルールとして蓄積する
- **対象**: Claude Codeで業務資料作成・開発タスクを行う実務者本人。将来複数プロジェクトを横断利用
- **制約**（前ターンでユーザー合意済み）:
  - 対象スコープ：複数プロジェクト横断管理（`config/projects.json` でプロジェクトパスを登録・切替）
  - フレームワーク：Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui + Recharts（Streamlit不採用、デザイン自由度優先）。`create-next-app@latest` 実行時点の最新版が Next.js 16.2.11 / React 19.2.4 だったためそれを採用（AGENTS.mdの指示に従い `node_modules/next/dist/docs/` で16系のRoute Handler破壊的変更を確認済み）
  - Webアプリ側はCPUモードでは外部API通信なし。ローカルJSON/MDファイルの読み書きのみ
  - GPUモード（Ollama連携によるルール矛盾検出＝機能3／Phase4）は**今回のスコープ外**。導線・型定義のみ用意し、実装は次回タスクとする
  - 初期データは仕様書記載のサンプルJSONをそのまま使用
  - 進め方：段階的Phaseではなく主要機能（機能1・機能2）を一括実装
- **auto_drive**: 明示指定なし。ただしハーネスのAuto Mode Activeが有効なため、都度の承認待ちはスキップし合理的判断で進行（判断根拠は本ファイルに記録）

## 仮定（未確定事項の自己補完）

1. `execution_log.json` は仕様書サンプルでは単一オブジェクトだが、時系列ログという性質上、実運用では複数タスク分蓄積されると判断。**配列で複数タスクを保持**する形に拡張する（サンプル1件を配列の初期値として格納）。一覧→詳細ドリルダウンのUIとする。
2. プロジェクトごとの `rules.json` / `execution_log.json` / `CLAUDE.md` の実体パスは、`config/projects.json` に登録した各プロジェクトルート直下に存在する前提とする（本仕様書のデータ構造定義に準拠）。
3. 複数プロジェクト管理のうち「本プロジェクト自身」もダミープロジェクトとして `sample-data/` を初期登録し、動作確認できるようにする。
4. ルールの「有効/無効」トグルは `rules.json` の `enabled` を書き換えるのみとし、`CLAUDE.md` 側は `enabled: true` のルールのみを本文に反映する形で同期する（無効ルールは `CLAUDE.md` に書き出さない）。

## 2周目：弱点を壊す

### 破壊者

実装物に対して型チェック(`tsc --noEmit`)・ESLint・vitest単体テスト・ブラウザでの実操作を行い、以下の弱点を発見・修正した。

1. **【重大】`fileIO.readJsonFile` の共有フォールバック変異バグ**
   `rules.ts`/`projects.ts` はモジュールスコープの定数（`EMPTY_RULES` / `DEFAULT_PROJECTS`）を `readJsonFile` の fallback 引数として渡していたが、`readJsonFile` はファイル未作成時（ENOENT）にその参照をそのまま返していた。呼び出し側が `rulesFile.rules.push(...)` のように返り値を直接変異させると、モジュール定数そのものが汚染され、**別プロジェクトの初回ルール作成時に前のプロジェクトのルールが混入する**という重大なデータ破損バグだった。
   vitestで `createRule` を複数回呼ぶテストを書いたところ「削除したはずのルールが3件残る」という形で顕在化。原因を特定し、`readJsonFile` が fallback を返す際に `structuredClone(fallback)` でディープコピーを返すよう修正（[fileIO.ts](../src/lib/fileIO.ts)）。
2. **base-ui Select の uncontrolled→controlled 警告**
   `ProjectSwitcher` の `<Select>` に SWR 未読み込み時 `value={selectedProjectId ?? undefined}` を渡していたため、データ取得完了時に制御状態が切り替わり警告が出た。ロード完了かつ `selectedProjectId` が確定するまで `<Select>` 自体をマウントせずプレースホルダーを表示する方式に変更して解消。
3. **Dialog/Tooltip の `asChild` 非対応**
   shadcn init のデフォルトプリセットが Radix ではなく `@base-ui/react` ベース（`-d` プリセット既定値）だったため、Radix由来の `asChild` パターンが型エラーになった。base-ui 流の `render` prop に置き換えて解消（`ProjectSwitcher`, `RuleCard`）。
4. **`react-hooks/set-state-in-effect` ルール違反**
   `trace/page.tsx`（初回選択タスクの決定）と `RuleFormDialog`（ダイアログ開くたびのフォーム初期化）でuseEffect内の同期的setStateがESLintエラーに。前者は「未選択なら先頭ログを使う」派生値に置き換え、後者は親コンポーネント側で `key` を張り替えてリマウントさせる方式に変更し、どちらもuseEffectを削除。
5. **execution_log.json のスキーマ後方互換**
   仕様書どおりの単一オブジェクト形式で書き込まれた場合でも読み込めるよう、`getExecutionLogs` に `{logs:[...]}` / 生配列 / 単一オブジェクトの3形式を吸収するフォールバック処理を実装し、vitestで3パターンとも検証。
6. **未対応のまま許容した点**
   Turbopackビルド時に `next.config.ts` 経由で「fileIO.ts の `process.cwd()` 呼び出しがプロジェクト全体をトレースする可能性がある」という警告が出る。本アプリはVercel等へのデプロイを想定しないローカル専用ツールのため実害なしと判断し、対応は見送った。

### 自己採点：90/100
（重大バグを実際に検出・修正できた点、型/Lint/テスト/実ブラウザ操作の4系統で検証した点を評価。減点理由はE2Eテストの自動化コードが無く手動確認止まりであること）

# ラウンド2：実データ対応（CLAUDE.md直接パース化 + スキル管理機能）

## 背景・方針転換の理由

ユーザーが実際の `~/.claude` フォルダ（`sample-data-user/.claude/`）を提供し確認した結果、**`rules.json` に相当する構造化ファイルは実際には存在しない**ことが判明。実際に存在するのは：

- `CLAUDE.md` — 自由記述のMarkdown（`## 見出し` ごとに1ルールのまとまり）
- `skills/<name>/SKILL.md` — YAML frontmatter（name/description/argument-schema）+ Markdown本文
- `settings.json`, `projects/*/*.jsonl`（生会話ログ）, `tasks/*/*.json` 等の運用ファイル

ユーザーへの確認の結果、以下の3点で合意：

1. **機能1のデータソースを `rules.json` から実際の `CLAUDE.md` 直接パース方式に切り替える**（rules.jsonは廃止）
2. **スキル管理（`.claude/skills/*/SKILL.md` の一覧・追加・編集）を新機能として実装する**
3. **機能2（実行ログ可視化）は現状維持**（`execution_log.json` の仕組みはそのまま残し、将来Claude Codeが出力する想定を維持）

## 1周目：方向性

### 戦略家

- 当初の仕様書設計（`rules.json` 中心）は「これから育てるメタデータ層」を前提にしていたが、ユーザーの真のニーズは「今あるものをそのまま見せる」こと。実データへの適合を最優先する。
- CLAUDE.mdは肥大化すると見出しの海になり全体像も有効/無効も把握しづらく、スキルも`.claude/skills/`を都度lsしないと何があるか分からない。これを一覧化・GUI化すること自体がそのまま価値になる。

### 設計者

- **CLAUDE.mdパーサー**：`# `(h1)はタイトルとして読み飛ばし、`## `(h2)を1ルールの境界とする。h2直下から次のh2（またはファイル末尾）までをそのルールのcontentとする。h3以下のネストはcontent内にそのまま保持し過剰パースしない。
- **無効化の表現**：セクション全体を `<!-- CCD:DISABLED ... -->` でコメントアウトすることで表現する（rules.json時代のようなJSONのenabledフラグではなく、Markdown自体に残す）。
- **ID割当**：見出しテキスト＋出現順インデックスを組み合わせて生成（永続IDではなく読み込みのたびに再構築するephemeral ID。並び替えは非対応）。
- **スキル管理**：`skills/<name>/SKILL.md` をディレクトリスキャンで列挙。YAML frontmatterのパースに `js-yaml` を追加。新規作成時はスラッグ化したディレクトリ名をバリデーション。
- **config/projects.json の個人情報漏洩リスク**：ユーザーが実際に「グローバル設定」として `C:\Users\sugur\.claude` を登録したことで、個人環境依存の絶対パスが `config/projects.json` に書き込まれた。このファイルは今までコミット対象だったため、**`.gitignore` に追加し `git rm --cached` する**（テンプレートは `config/projects.example.json` として別途コミット）。
- 主な失敗リスク：frontmatterの壊れたYAML→パースエラーをキャッチしエラーバナー表示に留める。スキル名の重複・不正なディレクトリ名文字→バリデーション。

### 生成者：3案比較（CLAUDE.md無効化表現方式）

| A. 見出し単位 + HTMLコメントで無効化 | シンプルで人間にも読めるMarkdownのまま、CLAUDE.md自体が唯一の真実源になる | **採用** |
| B. frontmatterにルールメタデータをJSON埋め込み | enabled等を構造化できるが、CLAUDE.mdは本来frontmatterを持たない自由形式なので互換性・可読性を壊す | 却下 |
